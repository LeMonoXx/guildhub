# AGENTS.md

Instructions for coding agents (and humans) working in this repository. Read this file fully before changing anything. Nested `AGENTS.md` files in `apps/*` add rules for that app; they never relax these.

## What this repo is

GuildHub: a website platform for one World of Warcraft: Forever guild per deployment. Traceless (`eu` / `traceless`) is the first instance. The target architecture is in [`docs/north-star.md`](docs/north-star.md). It is binding.

Today only `apps/api` exists (Hono, `GET /health`). Most of the north star is not built yet. Do not describe planned parts as existing.

## Commands

```sh
pnpm install                      # Node 24, pnpm via corepack (packageManager field)
pnpm verify                       # the gate: format, lint, types, tests, build. Must pass before you finish.
pnpm format                       # fix formatting
pnpm --filter @guildhub/api dev   # run the API with reload
pnpm --filter @guildhub/api test  # API tests only
```

If `pnpm` is missing on Windows: `corepack enable --install-directory "$env:APPDATA\npm" pnpm`.

Target (after the Aspire AppHost lands): `aspire start`, `aspire wait`, `aspire describe --format Json`, `aspire otel logs --format Json`, `aspire stop`. See [`docs/development.md`](docs/development.md) §6.

## Hard rules

1. **Secrets.** Never write a real client ID, client secret, token, cookie, or password into the repo, a test, a fixture, a log line, or an image. Configuration comes from the environment. Example values in `.env.example` and tests are obviously fake.
2. **Login is Battle.net OAuth only.** No own password login, no own OAuth protocol code. Use `arctic` as decided in [0005](docs/decisions/0005-battlenet-oauth-bff-sessions.md).
3. **No token in the browser.** The frontend never receives, stores, or sends OAuth tokens.
4. **Battle.net is the source.** Read Battle.net data through `@blizzard-api/wow-forever`. Do not scrape the Armory website or call its GraphQL.
5. **No guild in platform code.** Nothing under `apps/` or `packages/` mentions Traceless or hard-codes a guild, realm, or region. Instance data lives in `instances/<slug>/`.
6. **Layer and module boundaries** from the architecture documents are not optional. If a change seems to need a forbidden import, the design is wrong; restructure or ask.
7. **Errors** follow RFC 9457 with codes from the shared catalog. Never return ad-hoc error JSON, never leak stack traces or upstream bodies.
8. **No real Battle.net calls in tests.** Use fakes, MSW fixtures, or the Battle.net stub.
9. **Migrations are reviewed SQL** generated by drizzle-kit and committed. Never `drizzle-kit push` against anything but a throwaway local database.
10. **Do not weaken the gate.** Do not disable lint rules, skip tests, loosen `tsconfig`, or lower `minimumReleaseAge` to make something pass. Fix the cause.
11. **Dependencies.** Add a dependency only if the decision records or architecture documents call for it, or propose a record. Shared tool versions go in the `catalog` in `pnpm-workspace.yaml`. Releases younger than three days are rejected on purpose.

## How to add a backend feature

1. Find or create the module in `apps/api/src/modules/<module>/`.
2. Domain: types and pure rules, with tests.
3. Application: one use case file, its ports, its `Result` error union, with tests using fakes.
4. Contracts: request and response schemas and any new problem codes in `packages/contracts`.
5. Infrastructure: implement the ports (Drizzle, Battle.net adapter), with integration or fixture tests. Add a migration if the schema changed.
6. HTTP: the route, validated with the contract schema, mapping errors through the shared problem mapper, with HTTP tests.
7. Wire it in the module's `index.ts` and in `main.ts`.
8. `pnpm verify`.

## How to add a frontend feature

1. Decide the layer (`pages`, `widgets`, `features`, `entities`, `shared`) using the table in the frontend architecture.
2. Use the API only through `shared/api`; types from `packages/contracts`.
3. Cover loading, empty, error, and data states. Strings go into every locale.
4. Keyboard and screen reader access per WCAG 2.2 AA.
5. Component tests with MSW; extend the Playwright journey if the flow is user-visible.
6. `pnpm verify`.

## Definition of done

- `pnpm verify` passes locally, and CI is green after pushing.
- New behaviour has tests at the right level. Bugs get a test that fails before the fix.
- No rule above is broken; no boundary is crossed.
- Docs are updated when behaviour, commands, or architecture changed. If the change contradicts the north star, the north star (or a decision record) was updated in the same change.
- The final report says what was verified and what was not (for example "Docker build not run locally").
